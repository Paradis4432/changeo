## Resolved design findings

**PR1: complete identity lock set for current badges.** The original single-account `findCurrent(AccountId)` proposal did not specify a viable sequence when the public viewer differs from the profile subject. Actual `IdentityStore.lockAccounts` discovers guardians, locks the complete sorted account set, reloads it, then locks relationships/consents. Repeated calls which discover another account after canonical locks, or after a partial first account set, are insufficient.

The revised exact API is `PublicIdentityBadgeAccess.findCurrent(Set<AccountId> profileSubjects): Map<AccountId,PublicIdentityBadge>`. It requires an active caller transaction and is its first identity-locking operation. The new identity-owned service derives the viewer from trusted `SecurityProof`, adds it to the bounded complete subject set and invokes the existing internal store once. Subsequent viewer audience guards reuse the already covered set before canonical locks. Discovery never appends a subject, guardian or profile after locking; changed binding/set denies or retries in a fresh transaction. No existing identity source edit is necessary for this design.

The value exposes only allowlisted synthetic scope, check-record time, validity and fixed public synthetic provenance. Actual stored provenance contains an operator UUID (`LOCAL_SYNTHETIC_OPERATOR:<uuid>`); publishing that private string would violate P1. Unknown/invalid source scope or provenance must never become a public arbitrary label. Missing, expired, restricted or invalid evidence yields absence and grants no permission. Public opt-in is part of the approved immutable profile revision. A badge can expire while a read waits for canonical locks, so final view construction additionally requires `validUntil > Clock.instant()`. The revised plan/brief require a real blocked profile read crossing expiry, without acquiring identity locks after canonical locks.

**PR2: draft eligibility cannot become publication authority.** Actual `ModerationService.submitForReview` checks the supplied `AuthorContext` against the canonical callback, stores it immutably, and `ModerationWorker` reuses its persisted capability at activation. Passing NEW permission for a stored DRAFT revision creates an exact-context mismatch; submitting with stored DRAFT permission risks activation through weaker eligibility, including minor self-draft authority. Workbench's resource-level author cannot be copied into the new owner because guardian publication changes the actor between immutable revisions.

The revised plan explicitly puts `AuthorContext` on each immutable revision. Self drafts use DRAFT_REQUEST/DRAFT_OFFER; guardian-managed writes use NEW_REQUEST/NEW_PROVIDER_PARTICIPATION with the actual subject. Every submission target, including adult self publication, is a freshly prepared immutable NEW revision. Preparation uses current NEW eligibility in an identity-first canonical transaction and preserves the DRAFT history; existing submission runs afterward in a fresh owner transaction before canonical locks. Direct DRAFT submission and self-minor NEW preparation/submission deny. The persisted NEW context remains unchanged through activation. If submission fails, an exact idempotent prepared revision remains visibly unsubmitted and can be retried; no false queued state is shown.

New revision attachments require new exact `FileReference` bindings. Existing immutable files belong to their original content revision, and current `FileAccess` provides no pending-file adoption/clone authority. The revised plan therefore requires explicit reupload/rebind or explicit omission with truthful UI. It never silently carries a DRAFT file reference into the NEW revision or reads pending bytes through status permission. A later proposed adoption API would be a shared-contract change before affected edits.

**PR3: canonical callback must support historical evidence.** Actual operator evidence, cases, recall and appeals use a submission's original author context while the trusted current actor is an operator or historical participant. Requiring current proof actor to equal the original author, requiring the revision to equal current, or enforcing new-publication eligibility inside the generic callback would block legitimate evidence of older, paused or closed revisions.

The revised `lockRevision` validates retained immutable author/context/reference/kind/digest/files and canonical ownership under its lock. It does not itself demand current proof-actor equality or current revision. Each submit, activation, current-public, reportable and lifecycle path separately enforces its additional current actor/membership/lifecycle requirements. Generic operator evidence first guards the current focused reviewer, resolves exactly one owner, discovers immutable author context without authority, locks/revalidates its retained canonical revision, then locks the moderation barrier/submission and compares exact canonical versus snapshot payload/bindings. Auditor access remains metadata only. Current file reads retain their separate full byte transaction and safety checks.

**PR4: persisted search must revalidate its selection, not only public visibility.** A candidate approved pointer can change between indexed selection and protected projection. Returning the new public revision without checking the original query/filter/rank binding would return a nonmatching result; stale counts or offsets based on hidden Adult/Sensitive/pending rows would leak their existence. The existing `ModerationAccess.approvalForUpdate` locks a reference barrier and its submission together, so chaining it across canonical rows does not provide category-wide barrier-before-submission acquisition.

The revised plan discovers bounded `(resourceId, approvedRevisionId, subjectId, label, immutable filters/rank)` tuples without exposing them. It prefers a fresh protected transaction per candidate: complete badge/viewer/guardian set, current viewer audience guard, canonical resource, then its moderation barrier/submission. It revalidates the same approved pointer, immutable whole payload, label, lifecycle, query/filter and rank inputs. Changed tuples deny or retry fresh; they cannot silently inherit stale authorization or search selection. Bounded rank-ordered results assemble from independently current coherent snapshots; no atomic snapshot across the page is promised. Additional scanning uses bounded fresh transactions, and displayed continuation/count/page information derives only from revalidated eligible results. A multi-resource alternative requires achievable category-wide sorted locking and cannot use existing sequential API calls to invert it. No new generic locking framework is needed.

## Remaining design assessment

Exact-reference `ContentOwner.owns(ContentReference)` is viable nonlocking discovery. The registry selects exactly one matching owner among all handlers for the surface kind, denying missing and ambiguous matches. Owners recognize only their own retained immutable persistence; callbacks independently validate full binding under locks. Server-generated random resource IDs cannot be reassigned or supplied as new client-owned IDs. This preserves REQUEST_BODY workbench behavior and admits the real request owner; PROFILE_BIO also overlaps the installed independent test owner and needs the same handling. Recognition conveys no authorization. Unknown revision/kind/cross-owner spoof and intentional ambiguity need real behavioral coverage.

One bounded deterministic review snapshot covers every authored display/title/body/bio/tag/coarse-area/mode/availability/pricing/deadline/opt-in field and exact media binding. Each projected field and search vector comes from that same immutable approved revision. System-owned badges stay separate; future completed-job reputation is absent rather than fabricated. Existing 32 KiB/four-file review bounds must apply to the complete serialized payload, not only its body. Arbitrary realistic whole snapshots remain manual-review content under the actual synthetic policy; the developer brief preserves that boundary rather than introducing broad fixture-based automatic approval.

Canonical state owns subject, immutable revisions, current/approved pointers, version, idempotent command receipts and explicit lifecycle. Pause removes discovery/detail/share/ordinary byte availability; close denies new responses without destroying history; resume requires deliberate current eligible approved state. A delayed activation cannot change paused/closed lifecycle or activate an outdated revision. Old unchanged approved content may remain during pending edits unless recalled. The callback/current/activation separation above permits this design without weakening operator history access.

`ListingAccess.currentPublic(UUID)`, `requireOpenForResponse(UUID)` and controlled `historical(ContentReference)` return immutable values, never entities or reusable grants. The response operation requires the caller transaction and complete identity guards before canonical locks and verifies exact approved OPEN state. Later conversations/jobs still own actual participant subject/guardian permissions and membership in that same caller transaction; a historical listing reference does not authorize unrelated conversations/jobs or transfer payer rights. Closing and pausing do not rewrite future obligations. Any required future complete-lock-set/API expansion returns through root contracts.

The plan preserves F2/M1B audience semantics: General browsing is not erased merely by a restriction; Sensitive and Adult use their actual viewer guards; minors/age-unknown users cannot obtain Adult content. Current guardian/write eligibility does not imply public badge eligibility, byte access or unrestricted support payload. Historical controlled self/participant support remains independent of fresh publication eligibility. Existing ordinary reset-after-admission behavior is retained; administrator epoch-bound MFA/freshness remains stronger. Profiles import only behavioral identity APIs, never identity entities or repositories.

The ownership boundaries, typed immutable records, explicit states, standard PostgreSQL/Spring transactions, one source writer and lack of speculative completed workflows fit the shared quality policy. The plan leaves cohesive internal implementation freedom while fixing the risky contracts. No additional source takeover, vendor, dependency or production policy decision is needed for readiness.
