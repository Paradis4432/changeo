These results establish a concrete ordinary-state transaction defect; they establish neither readiness nor failure of every downstream behavior, because most tests stop in setup/preparation.

Current `MarketplaceReader.own` holds a caller transaction and current identity/canonical locks, then catches `ModerationFailure` from `moderation.approval` for each unsubmitted revision. Actual `approval` is a participating Spring transactional method. Its missing-submission exception marks the caller rollback-only before the local catch returns empty, so own-history cannot commit. Catching more exceptions or changing the old method's rollback policy would mask genuine denial rather than model ordinary absence.

The moderation owner already has the correct nonthrowing internal lookup: `ModerationStore.find(ContentReference, boolean)`. Its existing join resolves an exact reference/revision and returns Optional; its throwing `submission` wrapper is intentionally used by existing required-submission APIs. An additive optional behavioral boundary at this owner is appropriate, without duplicating submission-presence flags in catalog persistence.

## Exact viable contract and sequencing

`ModerationAccess.findApprovalForUpdate(ContentReference): Optional<Approval>` is additive. It requires an active caller transaction, current appropriate identity guards, and an already locked/revalidated exact canonical resource/revision. Identity guard/membership/provenance ownership stays with the caller; the method grants no permission and cannot be used as a lock-free discovery or public HTTP endpoint.

The service first resolves exactly one installed owner for the complete immutable reference. Unknown, ambiguous or nonexistent/wrong-kind references deny. A nonlocking moderation-local `find(reference,false)` may then distinguish absence. Legitimate absence returns empty without throwing, creating a barrier/submission/task, issuing content or poisoning the caller transaction. An existing barrier for a different revision does not turn this revision's absence into approval.

If a submission exists, the service locks the existing reference barrier and then reloads/locks the exact submission, using the same sequence as `approvalForUpdate`. It returns current immutable reference/digest and locked state/label/reason only. It must not lock the submission first and later its barrier. If a previously found record becomes invalid or disappears unexpectedly, that is a genuine failure, not a new successful absent-state fallback. Existing immutable reference/snapshot bindings and trusted submission ownership make the normal known-record identity stable. No schema or ModerationStore change is necessary for this design.

The caller's retained canonical resource lock is the negative-observation serialization point: all legitimate same-revision submission paths acquire that lock through the installed canonical callback before inserting the moderation snapshot/submission. A submission which commits first is visible to the later protected lookup; an own-history transaction which observes absence first prevents the competing submit from completing until it releases the canonical/identity locks. Background review results change existing status under barrier/submission locks and do not create a missing submission. Consequently absence requires no fabricated moderation lock row and cannot race a legitimate same-revision insert while the caller holds its canonical lock.

For known status, own-history compares `Approval.reference` and `digest` against the exact retained immutable revision and recomputed whole canonical payload before using label/state. It treats the locked current label as the input to its ordinary owned-content audience check. The complete actor/subject/guardian identity set must already be locked before canonical acquisition; post-canonical `identity.decide` may evaluate only that retained set and must not acquire another guard/account/guardian lock. This preserves current age/preferences/restrictions/guardian semantics without order inversion. The amended actual plan and developer brief now state these checks explicitly.

Absence remains conservatively unsubmitted/unknown for payload eligibility. DRAFT and prepared NEW states stay distinguishable from their immutable authorship; empty never means approved, queued, safe bytes or unrestricted body visibility. Known REJECTED/PENDING/RECALLED states may supply controlled own status under existing audience rules, but they cannot authorize public detail/search/share or ordinary attachment bytes. Known APPROVED metadata alone also does not substitute for full current public pointer/lifecycle/recall/digest/audience checks. Existing file-owned transactions and bridges remain unchanged.

Own-history is bounded to retained revisions of one locked resource, which share its moderation reference barrier. It must not acquire another canonical resource or identity set while holding moderation locks. The new scalar method does not establish a generic multi-resource batch lock protocol; any broader use must honor the already accepted sorted/category lock order and current caller preconditions.

Genuine invalid binding/authorization/owner failures still throw and roll back, even if a caller catches them. The new method may return empty only for the legitimate missing moderation record after trusted canonical validation. No blanket catch, noRollbackFor, REQUIRES_NEW escape from the owner transaction, cached permission or hidden transaction marker is needed. The old `approval` and `approvalForUpdate` signatures and required-record/rollback behavior remain intact.

## Alternatives and verification obligations

An existing-API conservative alternative is technically possible: discover status in a standalone transaction, then lock/revalidate known status inside the owner projection; on an uncertain absent race show only metadata with an explicit refresh/unknown state. It adds exception-based ordinary discovery, repeated transactions and stale-absence handling at every caller. A catalog-side presence flag duplicates moderation-owned state. The accepted Optional method expresses the required ordinary absence at its natural owner with less hidden coupling while preserving legitimate denials.

The same developer must add meaningful real PostgreSQL coverage before delivery:

- Unsubmitted DRAFT and prepared NEW lookup returns empty, the caller can commit an unrelated intent, and no reference/barrier/snapshot/submission/task row is created. Also cover absence for a newer revision when the resource already has an older moderation barrier/submission.
- Known lookup returns the exact reference/digest and current locked state/label; own payload projection compares/recomputes the whole binding. Label/recall/background-result races cannot return stale permitted content. Invalid digest/binding denies rather than becoming absent or approved.
- Both same-revision submit/absence orders use actual owner locks and real submission: absence-first holds its protected commit before submit, and submit-first makes the next own lookup see known current status. Release gates in finally and assert actual rows/results, not only timeouts.
- Missing caller transaction, unknown/wrong-kind/ambiguous owner and invalid binding deny. A caught genuine failure rolls back a caller intent with no partial moderation writes. Existing throwing APIs retain their prior absence/rollback behavior.
- Unsubmitted/pending/recalled status never grants public content or ordinary file bytes; own age/preferences/guardian/history restrictions still apply. Run the full existing moderation/foundations regressions and all new feature checks, including actual Testcontainers, with complete first logs and true exits.
