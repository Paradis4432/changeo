# M1C implementation clarifications

Read root M1C and local M1C. These local details preserve accepted owner/caller shape and fix concrete plan-review concerns; same plan reviewer reassesses before submit implementation.

The entire submit pipeline executes through a MANDATORY participating transactional boundary, not only the IdentityAccess guard. Any denied bridge/binding/canonical/admission/exact payload stage throws through that boundary and marks the caller transaction rollback-only even if the external caller catches it. Missing transaction fails before any effect. Successful identity guard alone does not protect later callback failure from partial owner commit. Normal callback writes and review snapshot/tasks commit atomically in their caller transaction; test caught failures at each meaningful boundary.

Canonical resource/revision creation in a submit transaction occurs inside the installed trusted callback after F2 identity guard; no earlier INSERT/flush that can take resource/FK locks. Alternatively, the workbench may have already committed an independent identity-first guarded private draft/intake transaction. A later fresh owner transaction then calls submit before resource locks and callback verifies that committed canonical revision. These are distinct user lifecycle actions, not a hidden callback closure/transaction marker. The chosen workbench uses separately guarded draft/intake followed by fresh submission. A saved draft with no successfully queued review has explicit DRAFT_PENDING_REVIEW metadata/status and actionable submit retry, cannot activate, emit a published signal or expose unsafe pending payload. A process stop/denied submit leaves the persisted draft visible as unsubmitted, rather than pretending worker review is queued. Draft/current pointer changes preserve previous approved unchanged pointer until recall. Explicit review replays retain task/exhaustion/attachment idempotency; new draft or retry generation has bounded actor/source admission. Test crash/denied submit, duplicate save/submit, restart and eventual successful protected submit.

There is no universal way for this API to detect arbitrary caller-held DB resource locks without speculative state/inspection machinery. Enforce identity-first ordering in every actual owned entry flow; require/document caller invokes submit before resource locks. Direct submit and concurrency behavioral tests prove those real paths. Future owner integrations independently test that precondition. Do not add pg_locks introspection, transaction marker registry, requireAuthor operation or identity API to claim universal detection.
