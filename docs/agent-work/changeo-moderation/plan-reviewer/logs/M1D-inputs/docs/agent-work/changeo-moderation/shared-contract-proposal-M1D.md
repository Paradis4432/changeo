## Installed behavioral owner operations

Generic moderation locks its stable reference barrier after canonical owner resource, then submission/task as applicable. Entire MANDATORY pipeline makes later callback/binding/admission failure rollback-only. Prior committed separately guarded draft remains allowed under M1C1; no hidden marker/token/identity API.

Activation starts fresh tx with persisted trusted submission AuthorContext F2 guard, then installed owner locks canonical resource/revalidates exact current revision/hash/files/author/membership/lifecycle. Moderation locks reference barrier->submission->task, validates current live approval/recall/claim/generation, then the same owner mutates its canonical approved pointer/version within this transaction; IDs-only signal and activation task completion commit together. Owner pointer operation does not obtain new locks or re-enter identity; it operates on the already locked owner resource. Missing owner cannot activate; stale/retired owner reference cannot publish different content. All positive approval sources share durable ACTIVATE owner.

Recall/operator current-binding changes use current focused identity guard then owner canonical resource lock, moderation reference barrier->submission->case/task. Owner invalidates its own approved pointer under existing lock; moderation invalidates approval and records evidence atomically. Normal content retrieval similarly resolves owner canonical current/approved pointer then current generic approval/reference/digest, not moderation pretending to own public content. Files.read retains M1A own transaction/current bridge, identity first, owner canonical resource next, moderation reference/submission next, bounded bytes/digest last; no outer transaction/reusable grant.

Background review result requires no identity or canonical pointer mutation: locks moderation reference barrier->submission->task, verifies immutable snapshot/live lease/claim, records exact decision/ACTIVATE intent. It never then obtains canonical resource lock. This stable review-reference row is the resource barrier for background result concurrency; results cannot publish by themselves. Foreground domain operations always canonical resource then moderator barrier then submission/task/case. Both orderings avoid reverse acquisition because background never proceeds from barrier to canonical. Sorted stable IDs apply within each owner/category; no identity after domain/record locks. This adds an explicit moderator reference barrier to M1's stable resource ordering, not an ownership transfer.
