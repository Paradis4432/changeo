## Material findings and expected correction

### MPR1 — P1: durable recovery between approval and activation

Location: `plan.md`, Architecture and state ownership, task lifecycle and separate automatic activation paragraphs; shared M1 proposal, Lock order and guarantees.

The review task becomes COMPLETE in the result transaction, whereas activation runs in a separate protected transaction. This separation is correct for identity lock order and current-author validation. The plan does not identify durable pending activation state, who retries it, or how a process that stops after committing approval but before invoking activation is recovered. The opaque decision signal alone does not fix this: delivery belongs to a future owner, and no current consumer/recovery contract for activation is defined. Likewise, approval-awaiting-eligibility status is useful but does not schedule a missing activation attempt. A transient activation transaction failure or restart can leave clear current content permanently approved but unpublished without an actionable author workflow.

Expected correction: retain the required two transactions and define the minimal moderation/workbench-owned durable activation recovery. For example, derive pending activation from persisted approved-current-reference versus approved pointer and let the opted-in worker perform a bounded idempotent sweep, with an explicit protected author retry operation; alternatively persist an activation intent atomically with the decision and process it after releasing result locks. Choose one coherent mechanism, not both overlapping state machines. An identity denial must roll back pointer/activation writes, preserve decision evidence, produce truthful status, and avoid an unbounded hot retry. Retry revalidates current identity, trusted persisted actor/subject/capability, membership, exact current revision/digest and recall under identity->resource->submission->task order. A stale reference becomes terminal/superseded rather than publishing a later edit.

Add real PostgreSQL tests for failure/crash after decision commit before activation, restart recovery, duplicate recovery, changed current revision, recall before recovery, transient failure, and identity-denied activation followed by deliberate permitted retry. No model re-review or duplicate signal is needed for the same immutable approved content.

This is a local clarification of M1's accepted approval/activation separation. If the selected mechanism changes externally consumed event shape/ownership or future owner guarantees, route that concrete amendment to root before implementation.

### MPR2 — P1: define one transaction owner for raw file reads

Location: `plan.md`, Coherent reads, recall and files; M1 raw file policy bridge and lock-order paragraphs.

The plan correctly requires locks through bounded text/byte materialization and forbids reusable grants. However, its bridge checks metadata/approval before files reads bytes without specifying which method opens and retains the transaction. A plausible implementation opens a transaction in the callback, returns a Boolean/decision, ends that transaction and then reads bytes, allowing recall/restriction to commit between approval and materialization. A second plausible implementation prechecks in the workbench, takes resource locks, invokes files, and invokes another identity guard in the bridge, violating the accepted order and introducing deadlocks with concurrent identity-first mutations.

Expected correction: specify one executable raw-read protocol and its normal/failure flow. Files' public read can own the transaction and invoke the current-policy bridge once before reading its immutable private artifact into bounded memory, with bridge identity/resource/submission locks retained in that same caller transaction; alternatively the owner can supply one active transaction while files invokes the bridge once and verifies mandatory transaction participation. In either case, no precheck acquires a resource lock and then re-enters a guard that acquires identity. The bridge must never retrieve bytes recursively. Fail closed on absent transaction/bridge, unrecognized owner, changed binding, failed current actor/MFA checks, quarantine, and digest mismatch. Return only fully materialized bounded bytes; lazy streams/async response bodies must not outlive the protected materialization transaction.

Operator safe evidence reads need the same explicit lifecycle: current focused role/MFA/freshness before resource/submission locks, one policy check, then bounded safe materialization. The auditor remains metadata only. A label of read-only transaction cannot substitute for actual locks; PostgreSQL SELECT FOR UPDATE and appropriate Spring transaction configuration must be compatible.

Add real PostgreSQL direct-files-boundary tests, not only controller precheck tests: hold policy/resource locks while byte copy is paused, attempt recall/current restriction or role removal, then verify both valid serialization orders. Assert that an independently invoked raw-read API denies missing/foreign binding and cannot bypass the bridge. This specifies M1's existing guarantee; it does not grant a new file-access capability or ownership change.

## Design assessment

The overall ownership design is sound and does not need a competing architecture. Immutable behavioral moderation/files values, canonical revision ownership in the consuming resource, separate review decisions/cases, and a deliberately synthetic persisted workbench preserve the original requirements while keeping unbuilt listings/conversations/jobs owners honest. The local task table is appropriate; a generic queue/vendor framework would not solve the actual owner-specific transitions. Append-only decision/case evidence, bounded safe metadata projections and opaque signals are appropriate extension points.

Current code substantiates the plan's foundation references. `IdentityAccess` exposes advisory decide/snapshot and mandatory caller-transaction requireForUpdate. `PermissionService` uses a MANDATORY TransactionTemplate, denies missing actor/subject, throws on denial and marks a joined protected transaction rollback-only. `IdentityStore.lockAccounts` discovers current guardian sets, locks complete sorted stable accounts through native PostgreSQL FOR UPDATE before refreshing JPA state, revalidates relationship discovery, then locks relationships and consents. It addresses absent-row/concurrent role/restriction facts without exposing repositories/entities. Current `IdentityPostgresTest` actually exercises both guard-winning and conflicting-mutation-winning orders plus caught-denial rollback. These are good references, not proof of new moderation behavior.

The existing focused roles are only IDENTITY_ADMIN, RESTRICTION_ADMIN and AUDIT_READER; current Capability has no moderation role values. Current ADMIN checks combine current self role, restriction, epoch-bound SecurityProof MFA and fresh password where required. Thus additive identity-owned F3 is necessary; role reuse would violate privacy and least privilege. Current local OperatorService generates unique passwords/factors, records epoch change and writes private enrollment material; the moderation implementation must consume the new accepted roles rather than reprovision identity through another owner. Current SecurityConfig/SessionEpochFilter/SessionProof provide framework sessions, current epoch invalidation, no-store/no-referrer, CSP, CSRF and trusted principal extraction. None is a substitute for current protected resource/role checks at the moderation boundary.

The accepted identity-first->resource->submission->task/case order is viable. Task-only SKIP LOCKED claiming in a short transaction, provider/synthetic work without database locks, token/generation/live-lease verification under stable result locks, and a separate identity-first activation transaction avoid a task->resource or moderation->identity cycle. Stale work must not activate current content. MPR1 asks for the durable handoff between these viable transactions, not a merger that would violate their responsibilities.

The plan's recall semantics are appropriately precise: a read that materializes under resource locks before recall may return its already-authorized response; every subsequent read after recall commit denies. This avoids an impossible promise to retract previously delivered bytes while enforcing current access at new retrieval. Search/detail/preview/notification/attachments must materialize through that owner boundary; no reusable URLs, cached excerpts or delayed bytes. MPR2 resolves the remaining transaction-lifetime ambiguity at files.

General/Sensitive/Adult is correctly separate from author permission, audience/membership and publication. Tattoo/medical/adult/prohibited cases, unknown/minor denial even for own pending raw payload, guardian non-override, and metadata-only status until eligibility is known preserve sources. The synthetic adapter is explicit opt-in and admits only labeled local fixtures; arbitrary content holds. Wrong schema/binding/scope, contradictory/prohibited approval, uninspectable bytes and outages hold/retry rather than treating model output as authority. Human approval must retain the same safe-file, exact-binding and prohibited-content guard; manual review is not authority to mark uninspected bytes safe. No model or moderation role may mutate money or identity restrictions.

Cases preserve reasons, appeals, ownership/version and append-only evidence. Restricted authors use controlled support eligibility plus their actual resource relation; report admission does not expose inaccessible private content. Own-content approval denial should compare the operator with both persisted author actor and subject, including guardian-authored submissions, as part of the planned explicit actor/subject binding. This is an implementation detail to verify, not a new product policy. A reversible warning/strike evidence record is distinct from identity restriction; account enforcement remains the explicitly authorized restriction owner.

Local file safety design is appropriately narrow: generated private opaque paths, immutable identity/digest binding, actual supported media validation, UTF8 and image dimensions/pixel bounds, quarantine for unsupported PDF/document/3D content, no active/raw unsafe operator preview. The current identity PrivateFiles helper is not a complete files reference: it has small private-factor/mailbox responsibilities and does not supply resource binding, bounded media inspection or full path/ancestor confinement. The builder should implement the files requirements at their own natural owner rather than importing identity persistence/private-secret helpers.
