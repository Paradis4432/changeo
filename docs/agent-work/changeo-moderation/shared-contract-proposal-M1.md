# M1 proposal: exact-revision moderation integration under S1/F2

Status: proposed; root decision required before affected implementation. No production policy or vendor is selected. Existing foundations are independently accepted. This proposal follows inspected current IdentityAccess, PermissionService, AdminService, IdentityStore and V1/V2 migrations.

## Existing and proposed ownership

Existing architecture assigns domain resources/revisions and participant access to listings, conversations/files, agreements/jobs and other resource owners; moderation owns decisions/cases; notifications/jobs owns delivery intents and safe retries. No current owner implements user content, files or background delivery.

Proposed moderation owns immutable review submissions (bounded text snapshot plus exact immutable attachment identities/digests), decisions, current review status, recall, reports/appeals, append-only decision/case audit and its durable review task. Each future resource owner keeps its canonical authored revision, availability/history/membership and current public/delivered pointer. Moderation never becomes owner of listings, message delivery, quotes/jobs or their lifecycle. Exact publication authorization is read through a behavioral moderation interface; a resource owner must bind that authorization to its own immutable revision and current resource/audience rules in its transaction. A retained older approval may remain usable while a new edit is pending, but recall invalidates every access channel immediately. Pending/stale review cannot move an owner's approved pointer.

A visibly synthetic private workbench is the only current consuming resource owner, kept in the moderation package as a local exercise. It has real persisted resource/current/submission/approved-pointer state and public/private audience fixtures; it does not create product profiles/listings/conversations/jobs. Anonymous approved-General retrieval is permitted only on loopback. Public/private owner behavior, previews/search and notification projections are exercised through actual guarded retrieval, with typed integration harnesses for all documented authored surface kinds. This evidence cannot establish end-to-end integration of unbuilt future owners.

Proposed narrow files owner supplies immutable quarantined synthetic artifacts and safe inspection through behavioral interfaces. It owns private byte storage, supported size/type checks, digest/identity, inspection/quarantine state and authorized byte retrieval. Moderation references attachments; it cannot mutate approved bytes or author storage paths. Future conversations/files owner retains membership, file references, retention and report context; it will consume this files boundary instead of receiving moderation's repositories. No retention period, production object store, arbitrary active preview or public media URL is selected. Supported text/plain and inert PNG/JPEG fixtures can be safely inspected locally; unknown/uninspectable 3D/document/active content remains quarantined/manual. Manual review may reject/hold but cannot declare uninspected bytes safe.

Durable moderation tasks use a moderation-local task table/worker with bounded attempts, leases, SKIP LOCKED safe claim and compare-by-claim-token completion. This is the moderation owner's initial job kind, not a replacement generic jobs framework. Provider work occurs outside DB locks; result commit locks the stable submission/resource and matches immutable revision/digests, current generation and live lease. No scheduled executor can bypass the explicit synthetic adapter opt-in. Publication/decision signals are appended in the same DB transaction with opaque resource/revision IDs only. Future notifications/jobs owns delivery state and consumes/revalidates these signals; no email/vendor delivery is built here and stored excerpts are forbidden. Repeated results/signals remain idempotent. Consumers fetch approved payload through current audience checks at delivery time.

## Behavioral interface shapes

ModerationAccess accepts immutable ContentReference(ownerKind, resourceId, revisionId), AuthorContext(actor, subject, capability, optional jobContext) and Submission(text, declared label, immutable attachment references, policy scope). Exact names/packaging are developer-owned; semantic shape is fixed. Every authored surface is explicitly represented: profile display/bio/media, offer/request title/body/media, public post/question/comment, completed-job review, quote description, job feedback, private message and attachment. Trusted transactional system events never use model authorization.

submitForReview requires an already-active resource-owner transaction, trusted server actor, current IdentityAccess.requireForUpdate and owner-supplied current resource/membership validation. Domain owners call this after their protected guard/locks in prescribed order; submission is idempotent by exact reference and digest and rejects altered payload for the same revision identity. No client may supply permission approval or private membership. This feature's workbench owns and verifies its own resource/membership and trusted actor.

approval/reference read returns only immutable status/approved label/digest/policy/model/reason codes; consumer resource owner retrieves its own canonical payload after matching digest. retrieve projection for the workbench applies both exact current approval and owner audience authorization at each public/detail/search/preview/notification/attachment path. General, Sensitive warning/preference and Adult identity/preference are separate. All NSFW retrieval including own pending preview/attachment must deny unknown/minor identities; operator evidence access uses its separate MFA role. Guardian cannot grant minor adult access. No membership grant may bypass content eligibility.

files intake/read use immutable FileId/digest and a trusted resource binding. Bytes cannot be replaced under an approved identity. Accepted metadata is bounded; content type uses actual bytes, not extension/client MIME. Supported image decoding is bounded against dimension/decompression abuse; output is inert/download only. Retrieval requires caller's current moderation/audience/resource decision and is request-scoped, no reusable grant outside protected access; workbench calls files only after checking exact attachment mapping. Quarantined/uninspected files never become ordinary downloads, previews or model input.

## Identity extension proposal F3

Current identity API has only ADMIN_IDENTITY/ADMIN_RESTRICTIONS/ADMIN_AUDIT. Reusing restriction or identity roles to read private content would violate focused least privilege. Proposed identity-owned capabilities ADMIN_MODERATION_REVIEW and ADMIN_MODERATION_AUDIT with corresponding MODERATION_REVIEWER and MODERATION_AUDITOR roles, same current role/restriction/epoch/MFA checks; review writes additionally require fresh password, audit read requires MFA. Identity still owns provisioning/removal/session epochs and role persistence. Moderation uses only IdentityAccess; no entity/repository sharing. Existing rights/capabilities remain byte-compatible except additive enum values. A new additive migration updates only identity role check constraints; V1/V2 immutable.

Root selected the responsible identity-owner path: same foundations coordinator/writer/final reviewer reopen the additive extension as F3. Foundation reserves V3; moderation owns V4+ only after F3 independently accepted and present. Moderation cannot edit identity source or V1/V2/V3. Required regression covers role provisioning/removal/current-role lock serialization, MFA/freshness, old role denials and all accepted foundations. No model output or moderation role may write identity restrictions or money; account enforcement remains explicit restriction-admin action with independent evidence/reasons/appeal.

## Lock order and guarantees

Foreground protected mutations: trusted actor/context and immutable resource identifiers; identity sorted stable account/guardian/consent locks first through current transaction; stable resource rows next in UUID order; submission rows next in UUID order; task/case rows last in UUID order. Preliminary resource discovery must be revalidated after identity locks. Never acquire new identity locks after a resource lock; no identity mutation acquires moderation/resources. Background review claims a task in short standalone transaction and releases it before work. Results commit in the same stable resource->submission->task/case order, without acquiring identity locks; a worker never holds a task while obtaining a resource lock. Background results approve the exact revision only. Separate protected publication activation starts a fresh transaction, revalidates persisted trusted author/current identity, owner membership and current revision, then acquires resource->submission->task order before pointer transition. Clear current content activates automatically through this transaction when still eligible; stale, recalled or newly ineligible content never activates. Result approval can remain historical evidence after activation denial.

Recall follows operator identity locks then resource->submission->task/case; it invalidates exact approval and any workbench approved pointer atomically. Author edits use identity->resource->submission->task. Report/appeal mutations use appropriate support identity guard, then resource->submission->case. Operator case review uses review-role identity guard then resource->submission->case/task; expected case/resource version prevents stale decisions. Read transactions resolve current resource/submission/audience in one coherent snapshot; attachment reads revalidate that binding before returning bytes. No path takes task/case then resource, and no result path takes moderation rows then identity.

Files independently invokes an AttachmentAccessPolicy behavioral contract on each raw read, using the trusted server security context and immutable file/resource/revision binding. The installed workbench/moderation bridge resolves current resource membership, exact attachment identity/digest, approval/recall and audience eligibility in a current read transaction; it cannot accept caller-submitted booleans, status or reusable grants. Unknown owner/reference or absent bridge denies. Ordinary retrieval additionally requires inspected-safe bytes. Only ADMIN_MODERATION_REVIEW may inspect bounded private review evidence after MFA/freshness; ADMIN_MODERATION_AUDIT reads bounded decision/case metadata with MFA and receives no raw payload/bytes. Uninspectable quarantined files expose metadata/reason only even to review operators in this synthetic slice; no ordinary or operator active preview/raw unsafe download. Future domain owners must install and independently test their current-binding bridge before using files reads; default remains denied.

Exact stale-result, recall-versus-retrieval, attachment replacement, lease-expiry/outage/retry and current-identity commit races require real PostgreSQL behavioral tests. Foundations preservation and whole application regression remain mandatory. Synthetic local policy/model input and technical limits are visibly testing-only and fail closed outside explicit sandbox opt-in. Production policy/Spanish model accuracy/privacy/vendor/retention/capacity remain Gate0.
