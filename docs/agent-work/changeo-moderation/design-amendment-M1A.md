# M1A: durable activation and one files-read transaction

Local design clarification within accepted M1. Addresses independent plan findings PR1/PR2; shared ownership/authorization/lock order unchanged. Read with plan.md. No implementation until same plan reviewer readiness and actual accepted/present F3.

## Durable activation after decision

An approved exact review result records decision and creates a unique durable ACTIVATE task for that revision in the same resource->submission->task transaction; successful REVIEW task completion alone cannot lose publication work. One moderation task table may hold REVIEW and ACTIVATE types with unique submission/type/generation idempotency. Claim remains standalone task-only, released before work. Recovery claims pending/expired ACTIVATE tasks after restart. ACTIVATE completion uses a fresh identity-first protected transaction, then resource->submission->task, validates live claim token/generation and expected current revision/approval/recall/pointer, and atomically transitions the pointer, inserts one IDs-only activation signal and completes the activation task. A crash before commit leaves work recoverable; a crash after commit cannot repeat pointer/signal effects. Superseded/recalled revision task becomes completed-with-no-activation or terminal according to an explicit reason, never resurrects content.

Identity denial rolls back the protected activation transaction. A distinct resource->submission->task result transaction then records awaiting-eligibility/manual state only if the claim remains current; it never changes pointer or grants eligibility. No cached failed/successful guard may authorize later activation. Bounded retries handle transient failure; eligibility/manual state stays visible without an endless automatic loop. Author can request reactivation of unchanged approved current revision through a current trusted-author permission guard and owner transaction; this queues a fresh ACTIVATE generation without reapproving or changing the immutable content. Changing content always requires a fresh REVIEW revision. Restricted users retain metadata/support/appeal while denied protected reactivation.

Tests deliberately separate result commit from activation, simulate lost worker/restart before activation and before/after activation commit, duplicate claims/signals, expired activation token, permission loss/winning restriction and author valid/invalid reactivation. All tasks follow M1 order; never hold task while obtaining identity/resource.

## Files raw-read transaction owner

Files.read is the sole raw-byte delivery entry. Its public behavioral operation must be called without an already-active transaction and fails closed otherwise; this prevents an outer resource precheck from holding resource locks and then re-entering identity. It starts and owns one current transaction. Within it, Files invokes AttachmentAccessPolicy exactly once with trusted server actor, exact immutable file/resource/revision binding and ordinary versus review-evidence purpose. The bridge acquires current identity guards first where authenticated/operator-required, then stable resource/submission read locks, verifies membership/approval/recall/classification and exact file identity/digest, and returns only bounded immutable storage metadata within that same transaction. No transaction closes inside the bridge and no reusable authorization/grant leaves it.

Files reads bounded immutable stored bytes and verifies size/digest before its transaction ends; identity/resource/submission locks remain held through that copy. It returns bounded memory only after successful commit. Opaque path is internal to files, never supplied by callback/client. Missing policy bridge, unknown resource owner, active caller transaction, wrong binding, unsafe inspection, file corruption or callback denial returns no bytes. Ordinary controller does no locking precheck; it calls Files.read directly. Operator safe evidence uses the same owner transaction with current review-role guard and exact evidence binding; auditor never receives bytes. Metadata-only preview/status operations do not open a files-byte path. Future owners implement their membership/approval bridge in this transaction rather than wrapping Files.read in a resource transaction.

Real PostgreSQL tests hold the bridge's authorized read after its locks, start recall and verify the writer cannot commit until byte-copy read releases; reverse order denies. Add current identity restriction/preference/epoch and private membership changes in both applicable orders, callback single invocation/transaction-lifetime assertions with behavior, no-active-tx denial, malformed binding/digest and missing bridge denial. Files bridge metadata path must not recursively read bytes or acquire identity after resource. This does not introduce a public URL/token or change future resource ownership.
