## Shared contract proposal (root acceptance required)

Identity/permissions owns account, contact-token, age/identity/provider-KYC evidence, guardian relationship, per-job consent, restrictions, preference, administrator MFA and append-only identity audit records. Later modules own resources, participant membership, legal agreement terms, billing entitlement, moderation approval and all money writes. No JPA entities/repositories cross module boundaries.

Expose behavior-level IdentityAccess interface with immutable IDs, PermissionRequest(actorId, subjectId, capability, jobId, fulfillmentMode), PermissionDecision(allowed, reason, actingAccountId, subjectAccountId, legalPayerId, evidenceScope) and AccountAccessSnapshot. Nullable optional context must instead use Optional/context records; exact internal Java packaging is builder-owned. Capability enum covers general/sensitive/adult viewing, request/provider drafting and new participation, marketplace messages, agreement acceptance, synthetic funding eligibility, job-specific in-person consent, existing obligations, support, financial-rights access and explicit administrator identity/restriction/audit actions. Decisions are identity permission only: they never approve publication, resource membership, legal terms, billing, financial entitlement or money movement. Callers combine identity decision with their own current owner checks.

Unknown/contact-unverified/age-unverified actors fail protected actions closed. Optional public badge, age evidence, guardian authority and provider KYC remain distinct. Adults require independently established sandbox adult evidence plus explicit preference for adult viewing. Minors never gain adult viewing. Under-16 provider actions always denied; 16–17 provider eligibility remains denied unless explicit synthetic legal/partner evidence and verified active guardian are present. Minor messages/agreements/funding require the verified active guardian as actor/legal payer; minor cannot act directly. Job-specific verified in-person consent cannot authorize another job or exceed legal eligibility. Revocation/restriction rejects new participation and stale sessions immediately while preserving controlled existing-obligation/support/financial-rights decisions and audit history. Later resource owners further constrain these reads; no blanket private-data bypass.

Identity facts and transitions are persisted with immutable provenance/scope. Guardian mutation and permission-sensitive updates use transactions and concurrency control. Permission checks reload current state; authentication session authority alone cannot preserve revoked powers. Admin operations require current least-privilege role, completed MFA, fresh authentication for security mutations and persisted audit. Synthetic bootstrapping is local-profile/explicit-option only; no web role self-grant. A separate fail-closed sandbox safety policy rejects non-loopback application binding, non-sandbox startup and every real-money mode even if configuration requests it. Future payment implementation must use this safety contract and add its own money boundary.

## Proposed endpoints and data shape

Server-rendered GET /, /register, /login, /account, /account/contact, /account/guardian, /account/preferences, /support, /rights, /admin/mfa, /admin/accounts and /admin/audit. POST /register, /logout, /account/contact/verify, /account/contact/resend, /password/forgot, /password/reset, /account/guardian/request, /account/guardian/{id}/revoke, /account/preferences, /admin/mfa and explicit /admin/accounts/{id}/eligibility, /restriction and /guardian-review actions. GET /password/forgot and /password/reset supply forms. Every mutation requires CSRF except framework-managed protocols if justified; owner-specific resources never rely on template hiding. URLs are private implementation contracts, no third-party API.

Proposed PostgreSQL tables: identity_account; identity_contact_token (purpose/hash/expiry/consumed state); identity_verification_evidence (type/status/scope/provenance); identity_guardian_link (guardian/minor/status/authority evidence/version); identity_job_consent (link/job/mode/status/version); identity_restriction; identity_admin_mfa (secret protected from exposure, last accepted counter); identity_audit_event. Account contains password hash and contact/setting facts, never raw credentials. Token hashes persisted; raw contact/recovery tokens delivered through local private mailbox adapter, never general logs or public anonymous inbox. Database referential constraints, normalized contact uniqueness, single-use expiring tokens and sensible field bounds are required. Exact migration SQL and indexes left to builder, but these ownership/data contracts need root decision before development.
